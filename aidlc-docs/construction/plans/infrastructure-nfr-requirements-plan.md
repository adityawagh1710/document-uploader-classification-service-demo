## A. NFR Requirements Questions

### Question 1 — CDK version pinning strategy
The CDK CLI + library versions must align (CDK is sensitive to version skew between `aws-cdk` and `aws-cdk-lib`).

A) **Exact pin for `aws-cdk-lib` + `aws-cdk` + `constructs`** — full reproducibility; manual updates only.

B) Caret pin for all three — accepts patch + minor; risks subtle CFN-template-diff changes between minors.

C) Exact pin for `aws-cdk-lib` + `aws-cdk`; caret for `constructs` (minimum-compatible peer dep). Standard AWS recommendation.

D) Other (please describe after [Answer]: tag below)

[Answer]: A — Rationale: CDK releases bring CloudFormation template-shape changes in minor versions (e.g., new properties added, defaults shifting). Exact-pinning all three means our snapshot tests are deterministic and the synthesised template can be reviewed line-by-line. Option C's caret on `constructs` follows the AWS recommendation but the `constructs` package rarely changes meaningfully — exact-pinning costs nothing. Option B invites silent template drift that we'd only catch via the snapshot diff (assuming we run the tests; people skip them when in a hurry). Aligns with U-2/U-3's exact-pin policy on AWS SDK.

### Question 2 — cdk-nag version pinning
cdk-nag rule packs evolve — new rules are added in minor versions.

A) **Caret pin (`^2.x`)** — accept patch + minor updates. New rules surface as warnings; we either fix or document suppression.

B) Exact pin (`2.30.0`) — full control over rule changes; harder to keep up with AWS guidance.

C) Other (please describe after [Answer]: tag below)

[Answer]: A — Rationale: cdk-nag's value is partly that it grows with AWS best-practice changes. Exact-pinning (B) means we miss new rule additions that AWS publishes for security or compliance reasons. The caret update model is safe because new rules surface as build warnings (not failures by default until promoted to errors); we get a chance to react. The 2 documented suppressions (IAM4 + L2) are stable; new cdk-nag rules don't disturb them.

### Question 3 — Deployment automation strategy
`cdk deploy` can be triggered manually or via a pipeline. Choose:

A) **GitHub Actions workflow with manual approval before prod** — `cdk deploy` runs in CI; dev/staging deploys auto-trigger on merge to main; prod requires manual workflow_dispatch approval. Aligns with the existing CI/CD model.

B) AWS CodePipeline with CodeStar source action — AWS-native; more setup.

C) Fully manual via `cdk deploy` from developer machines — fastest for prototypes; loses audit trail and per-PR validation.

D) Other (please describe after [Answer]: tag below)

[Answer]: A — Rationale: GitHub Actions matches the existing CI choice (U-1 + U-2 + U-3 all assume GitHub Actions). Manual approval before prod is the standard production-grade pattern — combines automation (no manual `cdk deploy` for the 95% case) with safety (humans-in-the-loop for the 5% case where they need to be). CodePipeline (B) adds an AWS-side workflow surface that duplicates GitHub Actions for marginal benefit on a small service. Manual deploys (C) are unauditable.

### Question 4 — Snapshot test stability strategy
CDK snapshots can drift between cdk-lib versions, between environments (CDK injects `Aws::Partition`, `Aws::Region` placeholders), and between machines. Choose strategy:

A) **Snapshot with `Match.anyValue()` for known-unstable fields** — e.g., S3 bucket name auto-generated by CDK uses a hash; that hash is masked in the snapshot to prevent thrash. Snapshots committed; reviewable.

B) Strict snapshots — fail on any drift; force re-snapshot via CLI flag. Catches more regressions but creates churn.

C) No snapshots; only fine-grained assertions. Loses drift detection for unintended changes.

D) Other (please describe after [Answer]: tag below)

[Answer]: A — Rationale: `Match.anyValue()` (and similar `Match.absent()`, `Match.objectLike()`) lets us mask CDK-internal noise (auto-generated logical IDs, regional placeholders, asset hashes) while still tracking semantically meaningful drift. The snapshot becomes a contract on the *shape* of the synthesised template — exactly what we want it to do. Option B's strict snapshots produce diffs whenever someone deploys to a different region or a CDK minor bumps; option C loses the cheap drift-detection that snapshots provide.

### Question 5 — Coverage targets for CDK code
CDK code is declarative; traditional branch coverage doesn't map cleanly. Choose:

A) **No coverage threshold on `infra/**`** — the test guarantees come from snapshot diff + fine-grained assertions, not branch coverage. The `cdk-nag` aspect at app-level provides additional structural verification.

B) Apply 70% branch coverage on `infra/**` — uniform threshold across all units. Will produce meaningless metrics.

C) Coverage limited to test files (assertions execute every code path) — circular: tests cover themselves.

D) Other (please describe after [Answer]: tag below)

[Answer]: A — Rationale: Branch coverage on CDK code is a category error — CDK constructors have minimal branching beyond `if (envConfig.X)` conditionals (which the snapshot tests against each environment cover). Forcing a coverage threshold here would push toward test-busywork without improving quality. The combination of snapshot tests + `Template.hasResourceProperties` fine-grained assertions + `cdk-nag` is the canonical CDK test strategy and is what we'll use.

### Question 6 — CI gates for U-4 specifically
The full CI workflow now has many jobs (from U-1 + U-2 + U-3). Which gates does U-4 add or change?

A) **Three new gates**:
   - `cdk-synth` — runs `cdk synth -c env=dev` to ensure the CDK app synthesises without errors
   - `cdk-nag` — runs `cdk synth` with cdk-nag aspect; fails on any non-suppressed violation
   - `infra-tests` — runs `vitest run infra/lib/**/*.test.ts` (the CDK stack snapshot + assertion tests, in `infra/` not `tests/`)
   Plus the existing `verify-bundle` job already added in U-3 NFR Reqs.

B) One mega-gate combining all of A — simpler CI; harder to see what failed.

C) Skip cdk-nag in CI; run it in a nightly job. Misses the per-PR safety net.

D) Other (please describe after [Answer]: tag below)

[Answer]: A — Rationale: Three separate jobs make failures legible: a `cdk-synth` failure is a CDK code bug; a `cdk-nag` failure is a security/compliance regression; an `infra-tests` failure is a snapshot drift or spec violation. Combining them (B) loses that signal. Running cdk-nag nightly (C) lets violations land in main before someone notices; that defeats cdk-nag's safety-net purpose. Each gate is fast (~10s to 30s of CI time per gate).
